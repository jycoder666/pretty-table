## 1. 背景

用户反馈：希望页面交互更饱满，不只是「选模板 + 换肤」；要对表格内容做自定义（含**合并**），并希望挖掘可集成能力。

本文**只谈可行性与分层成本**，对照现有定稿契约；**不催开干、不改 ADR 结论**。若某能力需扩范围，标「建议修订」待拍，**禁止写成已采纳**。

定稿已含（非「只有选模板换肤」）：槽位改字、三套色、**有限合并**（`layout.allowedMerges`）、表内区块槽、另存本机模板、导出 HTML/PNG。VTable 作主核（ADR-001）。

---

## 2. 分层口径

| 层 | 含义 | 典型职责 |
|----|------|----------|
| **核** | VisActor VTable 的 option / API | 渲染、合并视觉、多级头、钉列、主题映射、（可选）原生单元格编辑 API |
| **壳** | App Shell + template-store + UI | JSON 约束（`allowedMerges` / `rowCount`）、属性面板、有限合并入口、DnD、禁操作文案、OUT 边界 |
| **适配层** | `TemplateJSON` → VTable `option` | 把 slots/blocks/layout/merges/theme 转成 columns/records/customMergeCell/theme；导出同源 |

硬规则（ADR）：**VTable 只渲染；壳管约束与交互；真相源在 template-store，不在 VTable 内部状态。**

---

## 3. 能力表

相对本期成本：低 = 契约已有、主要做壳体验；中 = 核有 API、须适配+映射；高 = 破 OUT / 改数据模型 / 近电子表。

| 能力 | 核支持度 | 壳职责 | 相对本期成本 | 与定稿关系 |
|------|----------|--------|--------------|------------|
| **槽位改字（填空）** | 核只显示；改字走 `setSlot` 再刷 option | 属性面板 / 失焦写 store | **低** | **本期主路径**（FR-03） |
| **VTable 原生单元格编辑**（`editCellTrigger` / `startEditCell`） | **有** [外](https://visactor.com/vtable/faq/23-How%20to%20edit%20a%20table%27s%20cell%20with%20VTable)：可开编辑触发、命令式开编 | 须把编辑结果**映射回 `slots`**；禁双源；未映射槽只读 | **中** | 可用作「表内点改」体验加深；**不得**绕过 store |
| **有限合并**（`allowedMerges` 内） | **有**：`customMergeCell` / 合并单元格 [外](https://www.visactor.io/vtable/guide/custom_define/custom_merge) · [外](https://www.visactor.io/vtable/guide/basic_function/merge_cell)；由 option 驱动 rowspan/colspan 类效果 | 面板只暴露 ⊆ `allowedMerges`；超界 → `MERGE_NOT_ALLOWED`；`structuralMerges` 不可拆 | **低～中** | **FR-03 已锁**；体验可加深（面板可感） |
| **任意格拖合并** | 核可改 merge，但无「Excel 拖合并」产品壳 | 须新手势+任意 range 写 JSON；与 OUT-9 冲突 | **高** | **OUT-9**；须另立项 + **建议修订**待拍 |
| **多级表头** | **有**（VTable 多级 columns） | 模板底稿定义；壳一般不运行时改层数 | **低** | **FR-04**；模板内置 |
| **增删行列** | 核可改 records/columns 长度 | 须改 `rowCount`/`colCount`、重算 slots/blocks/merges；属性面板**禁止**入口（开发约定） | **高** | **OUT-1**；踩定稿；另立项 |
| **列宽 / 行高拖拽** | **有**（列宽拖拽等交互配置常见） | 是否写入 JSON 持久化、导出 HTML 是否带宽 | **中** | 未锁；可评估后置，不破壳核 |
| **钉列 / 冻结** | **有**（`frozenColCount` 类） | 模板 `layout.frozenColCount`；壳开关若做须 ⊆ 约定（≤2） | **低** | 契约已有；体验可加深 |
| **主题换皮 `themeId`** | 核吃 theme token | 壳切换 `T-A/B/C` → `applyTheme` | **低** | **pack-A3 已锁** |
| **表内区块槽（customLayout / 自定义单元格）** | **有**（自定义单元格 / 布局扩展） | 壳 DnD + `blocks[]`；核只渲染 | **中** | **U-6=A / FR-08**；已锁 |
| **公式 / 筛选排序（电子表向）** | VTable 偏展示；完整公式/业务网格非主定位 | 若强做易滑向 FortuneSheet/Univer 心智 | **高** | **OUT-2 / OUT-4**；本期不做 |

---

## 4. 结论建议（非拍板）

1. **加深体验优先走「壳把已有契约做满」**（不改 ADR）：有限合并面板可感、单元格强调/对齐、钉列与横滚体感、区块库交互打磨。  
2. **原生单元格编辑可用**，但必须：编辑结束 → 映射 `slotId` → `setSlot` → store 为唯一真相；**禁止** VTable 内 records 与 `slots` 双源。未建映射的格保持只读。  
3. **增删行列 / 任意格拖合并** = 高成本且踩 **OUT-1 / OUT-9**；须产品另立项；可能牵动需求 FR 与数据模型（`rowCount` 锁死等）。  
4. **列宽拖拽**可作后置评估项：核支持、壳决定是否持久化进 JSON；不破 ADR。  
5. **公式/筛选排序**维持 OUT；勿为「饱满」引入电子表主路径（ADR 已弃 FortuneSheet/Univer 作本期主核）。

## 5. 是否修订 ADR

| 判断 | 说明 |
|------|------|
| **本期：不建议修订 ADR-001** | 主核 VTable + 壳核分层 + 有限合并/槽位填空已覆盖「更饱满」的主路径；加深在壳与适配层即可 |
| **仅当用户坚持**任意合并或运行时增删行列时 | 才进入下方「建议修订」待拍清单（**未采纳**） |

### 5.1 「建议修订」待拍项（仅用户坚持时启用 · **非已采纳**）

| ID | 建议修订对象 | 内容摘要 | 触发条件 |
|----|--------------|----------|----------|
| **REV-A** | 需求 OUT-9 / FR-03 | 允许模板外任意格合并或拖合并 | 用户明确要 Excel 式合并 |
| **REV-B** | 需求 OUT-1 / `layout.rowCount` 锁死 | 允许运行时增删行列 | 用户明确要自由改表结构 |
| **REV-C** | ADR-001 / 开发约定 CoreHandle | 扩 `insertRow`/`deleteCol` 或通用 `setLayout`；适配层复杂度显著上升 | REV-A 或 REV-B 拍板后 |
| **REV-D** | 主核选型（ADR） | 若重编辑成主叙事，重新评估 FortuneSheet/Univer（**高风险**，易变弱 Excel） | 仅当 B+A 轻编辑叙事被推翻 |

**当前默认：REV-\* 全部未启用；ADR 结论不变。**
