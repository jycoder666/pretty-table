## 2. 脚手架方案对比

| 维度 | A. create-vue（单工程，目录分壳/核） | B. create-vite react-ts | C. A + pnpm workspace（壳、核两包） | D. 重型：Nuxt / Next / vben 等后台模板 |
|------|------|------|------|------|
| 许可证 | ✅ MIT（模板 CC0，见 Q1） | ✅ MIT | ✅ 同 A | ✅ MIT，但连带依赖多，逐个审 OUT-7 成本高 |
| 维护活跃 | ✅ Vue 官方，昨日有推送 | ✅ Vite 官方 | ✅ 同 A | ✅ 活跃 |
| 接 VTable | ✅ `@visactor/vue-vtable` 官方封装 | ✅ `@visactor/react-vtable` | ✅ | ⚠️ 可接，但 SSR 框架需关掉服务端渲染处理 canvas |
| TS + Vitest 开箱 | ✅ 生成时勾选 TS / Pinia / Vitest / Playwright / ESLint | ⚠️ TS 有，Vitest/测试需手补 | ✅ 同 A，多一层 workspace 配置 | ⚠️ 各自体系，配置重 |
| 纯静态部署 / 嵌入 | ✅ `vite build` 出静态文件 | ✅ | ✅ 核可单独打包，嵌入最顺 | ⚠️ Nuxt/Next 可静态导出但为 SSR 设计；后台模板带登录权限路由，违背 C1 |
| 体积 | 小（只装勾选项） | 小 | 小 | 大（后台模板自带整套 UI 库、权限、菜单） |
| 学习成本 | 低 | 低～中（需换 Uiverse 约定为 JSX） | 中（workspace、包间引用、构建顺序） | 高 |
| 防「一次堆满」 | ✅ 问答式勾选，不勾不装 | ✅ 模板最简 | ✅ | ❌ 删比写累 |
| 契合 C5/C7 | ✅ | ⚠️ 需改 C7 | ✅ | ❌ 整套 UI 库盖主题 |

**结论：推荐 A。** B 为改用 React 时的对应方案；C 留作 U-4 嵌入真正立项时的演进形态（从 A 抽 `src/core` 为独立包，迁移成本低）；D 放弃。

放弃理由：
- **B**：能力等价，但与 C7（Vue SFC）和设计增量 §6.1 推荐不一致，换它要连带改交互取用约定；无明显收益。
- **C（现在就拆）**：U-4 目前仅「CoreHandle 概念预留、不进本期验收」，提前拆包增加配置与构建复杂度，收益要到嵌入立项才兑现。
- **D**：Nuxt/Next 为服务端渲染与路由而生，C1 下用不上；vben / element-admin 类自带登录、权限、菜单与整套 UI 库，违背 C1、C5。

## 4. 落地默认（我按默认写入，异议请提）

1. **create-vue 勾选**：TypeScript ✅、Pinia ✅、Vitest ✅、Playwright ✅（端到端验「导出 = 预览」）、ESLint ✅、Prettier ✅；JSX ❌；Router 见 Q3。
2. **目录**：`src/core`（TemplateJSON store、toOption、导出、格式化；不依赖 Vue 组件）与 `src/shell`（页面、组件、交互）；用 ESLint 的导入限制规则（`no-restricted-imports`，ESLint 内置，零新增依赖）禁止 `core` 引用 `shell`。
3. **包管理**：pnpm，单工程；锁文件入库；Node 版本写入 `.nvmrc` / `engines`（具体版本开码时按 create-vue 当期要求定）。
4. **许可检查**：开码后加一条脚本检查依赖许可证只含 MIT/Apache-2.0（工具选型开码时再比，不在本期文档范围）。
5. **首个 PoC（脚手架搭好后第一件事）**：vue-vtable 渲染 + 3x 出图 + 透明底；@dnd-kit/vue 键盘拖拽；Reka UI 抽屉焦点回收 + Toast 读屏。三项任一不过，回流架构换备选。

### 7.2 逐项推荐

| # | 事项 | 推荐 | 放弃项与理由 |
|---|------|------|--------------|
| 1 | 前端框架 | **Vue 3 + Pinia**（同 Q4） | React + Zustand：能力等价，但要连带改 Vue 单文件取用约定，无收益 |
| 2a | Router | **不勾**；编辑台 / 模板库 / 导出用组件内状态切换 | vue-router：只有要求「各页可直达网址」才需要，需求里没有 |
| 2b | 端到端测试 | **Playwright**：create-vue 可直接勾选；自带截图比对（`toHaveScreenshot`），可直接比「预览 vs 导出 PNG」；多浏览器 | Cypress：截图比对要另装插件，多浏览器支持弱一些 |
| 3 | Tailwind | **不引入**；Uiverse 片段改写为我方色板变量（与交互意见一致） | Tailwind：多一套默认色与间距体系，与「色板唯一来源」冲突 |
| 4 | 组件库 | **Reka UI**（同 Q5） | Headless UI Vue：组件少、无 Toast、仓库约半年无推送 |
| 5 | 模板本机存储 | **IndexedDB + idb-keyval**（Apache-2.0，极小，只做键值读写）；外面包一层 `TemplateRepo` 接口，以后换实现不动业务 | localStorage：同步阻塞、通常只有约 5MB 且只能存字符串，「只新增」模板会越存越多 **[? 容量以浏览器实测为准]**；Dexie：功能远超所需；localForage：两年多无维护 |
| 6 | 交付形态 | **普通静态网页**（`vite build` 输出），本期唯一验收形态 | 单个 HTML 双击打开（vite-plugin-singlefile，MIT）：可作后续可选项。风险是 `file://` 下浏览器对本机存储与剪贴板的限制各不相同 **[? 待 PoC]**；如果要打包字体，文件也会很大 |
| 7 | 色板单一来源 | 在 `src/core/theme/` 放一份 **T-A/B/C 色板数据（TS 对象）**，同时生成三样东西：①壳的 CSS 变量（`:root[data-theme]`）；②VTable 主题配置；③导出 HTML 的内联样式。预览、PNG、HTML、外壳四处同源 | 运行时从 DOM 读 CSS 变量（`getComputedStyle`）再喂 VTable：核会反过来依赖壳和 DOM，违反 ADR-001 分层，离屏出图时也读不到 |
| 8 | 中文字体 | **系统字体栈**（如 PingFang SC / Microsoft YaHei / Noto Sans CJK SC），由同一个字体常量供画布、PNG、HTML 三处使用；导出前 `await document.fonts.ready` 后再重绘出图 | 打包网络字体（思源黑体 / Noto Sans SC 等）：许可多为 **SIL OFL**，不在 OUT-7 名单内（见 Q6）；单个字体就有数 MB，需要做子集化 |

**门禁规则（写入，不需选择）**：
- **G-1 核不得引用壳**：`src/core` 不得引用 `src/shell`。用 ESLint 内置的 `no-restricted-imports` 强制检查，CI / pre-commit 不通过就拒收；Vitest 加一条用例校验 core 的导入图（实现细节开码时定）。
- **G-2 色板单一来源**：T-A/B/C 只在 `src/core/theme/` 存一份 TS 色板数据，由它生成壳的 CSS 变量、VTable 主题和导出 HTML 的内联样式；禁止在别处硬编码色值，也禁止运行时从 DOM 反读 CSS 变量（理由见 §7.2 第 7 行）。评审时搜到别处的色值字面量就拒收。

### 7.3 字体的已知限制（如实说明）

- 系统字体栈下，**同一台电脑**上预览和导出一致；换了系统（Mac / Windows）字形会不同。导出的 HTML 在收件人电脑上也用他们的系统字体，这一点任何方案都无法完全消除，除非嵌入字体。
- 想做到「跨电脑像素一致」只能嵌字体，但会碰到许可证和体积两个问题，所以列为待确认 Q6。

### 7.4 字体对 PNG 离屏重渲染的影响

- 离屏 VTable 实例与预览用**同一个字体常量**（来自 `src/core/theme`），不允许离屏另设字体。
- canvas 绘制**不会主动触发**网络字体下载：字体没加载完就绘制，备用字形会直接画进 PNG，事后也无法纠正。所以出图顺序固定为：`await document.fonts.ready` →（打包字体时再 `await document.fonts.load('<字号> <字体名>')`）→ 创建离屏实例并渲染 → `exportImg`。
- 选系统字体时不需要下载，上面的等待几乎是零成本，但仍保留这一步，作为以后换网络字体的保险。
- 选打包字体时，首次导出会多一次字体加载的等待；要配合导出中的状态提示（交互的 S 状态），超时就按 `EXPORT_*` 失败码处理（具体码开码时补，不在本文定）。
